# Internationalization / Localization (B13)

Additive i18n for OB-CMS: per-site locales, per-locale page/post translations,
locale-prefixed public URLs + hreflang, and an admin locale switcher. **Existing
single-locale content keeps working unchanged** — every default is chosen so a
site that never touches i18n behaves exactly as before.

## Locale model

A site's locale set lives on `site_settings`:

| column          | type           | default   | meaning                                            |
| --------------- | -------------- | --------- | -------------------------------------------------- |
| `default_locale`| `varchar(12)`  | `"en"`    | canonical locale, served WITHOUT a URL prefix      |
| `locales`       | `jsonb`(text[])| `["en"]`  | every locale the site publishes (incl. default)    |

Codes are lowercase BCP-47-ish (`en`, `es`, `fr`, `pt-br`). The service
(`normalizeLocales`) always forces `default_locale` into `locales`, dedupes, and
falls back to single-locale `["en"]` for legacy/null rows.

- Read/write (site_admin): `GET|PUT /sites/:siteId/locales`.
- Exposed publicly on `GET /api/v1/public/site` as `site.defaultLocale` + `site.locales`.

## translationKey grouping

`pages` and `posts` each gain:

- `locale` (`varchar(12)`, default `"en"`) — that row's language.
- `translation_key` (`varchar(50)`) — a shared id grouping all translations of
  one **logical** page/post. Siblings share the key and differ by `locale`.

A "translation" is therefore just **another row** with the same `translation_key`,
a different `locale`, and its own `slug`/`layout`/`seo`/`status`.

Slug uniqueness was relaxed from `(site_id, slug)` to **`(site_id, locale, slug)`**
so `/about` (en) and `/es/about` (es) can coexist. Single-locale sites are
unaffected (locale is constant). Index `(site_id, translation_key, locale)` backs
sibling lookups.

### Endpoints

- Pages/Blog list accept `?locale=` to filter to one locale.
- `POST /pages/:id/translations { locale, slug? }` — clones the source row into a
  new locale: new id, **same translationKey**, target locale, copied layout/seo as
  a starting point, `status=draft`. 400 if the locale isn't enabled, 409 if a
  translation in that locale already exists. Same for `POST /posts/:id/translations`.
- `GET /pages/:id/translations` / `GET /posts/:id/translations` list sibling locales.
- Existing create/update/publish keep working: new content is authored in the
  site's `default_locale` and starts its own group (`translationKey := its own id`).

## URL scheme

- **Default locale → NO prefix** (`/about`, `/` for home) — backward-compatible.
- **Other locales → `/<locale>/<path>`** (`/es/about`, `/es` for the es home).

The renderer catch-all (`app/[[...slug]]/page.tsx`) peels a leading path segment
iff it matches one of the site's **non-default** locales; the remainder is the
locale-agnostic content path resolved against the API (`?path=&locale=`).

## Fallback behavior (DOCUMENTED CHOICE: fall back to default)

`GET /api/v1/public/page?path=&locale=` resolves in this order:

1. published page for `(site, requested-locale, slug)`;
2. **else** the published page for `(site, default-locale, slug)` —
   **fallback-to-default**, so a partially-translated site never 404s a known
   route (it serves the default-locale content under the requested-locale URL);
3. **else** 404.

`GET /api/v1/public/posts/:slug?locale=` uses the same policy. The response carries
the `locale` actually served (may differ from requested on fallback).

## hreflang

The public page response includes `alternates`: one entry per available
published translation of the logical page — `{ locale, path }` with `path`
already prefixed (default locale unprefixed). The renderer turns these into:

- `<link rel="alternate" hreflang="<locale>" href="…">` for every translation,
- `<link rel="alternate" hreflang="x-default" href="…">` → the default-locale URL,

via Next `metadata.alternates.languages`. `generateMetadata` also sets
`og:locale` to the served locale. The public blog index lists default-locale
posts only (no duplicate cards across locales).

## Migration & backfill — `0017_i18n_localization.sql`

Idempotent (`IF [NOT] EXISTS` / guarded `DO` blocks). Steps:

1. add `site_settings.default_locale` (`'en'`) + `site_settings.locales` (`["en"]`).
2. add `pages.locale`/`pages.translation_key` + `posts.locale`/`posts.translation_key`.
3. backfill `locale := owning site's default_locale` (fallback `'en'`).
4. backfill `translation_key := id` for every existing row → **each existing
   page/post becomes its own single-locale group**.
5. relax slug uniqueness: drop `(site_id, slug)`, add `(site_id, locale, slug)`.
6. create `(site_id, translation_key, locale)` indexes.

After it runs, every legacy page/post is `locale=<defaultLocale>`,
`translationKey=<id>`, and still renders at its current URL with no prefix.
