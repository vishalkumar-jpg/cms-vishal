## 0. Intent

```text
Choose Template (this catalog)
  ↓ copy
Page instance (independent)
  ↓ composed of
Sections (PR #18) → Components (PR #17) → Blocks → Content
```

Operators create pages from named starters instead of rebuilding layouts. Engineering adds templates as catalog entries without forking components or redesigning ownership.

---

## 1. Template behavior (agreed in PR #15–#16)

| Rule | Behavior |
|------|----------|
| **Create** | Selecting a template **copies** its section structure, defaults, placeholders, and default Reusable Block refs onto a new page |
| **Independence** | After creation, the page is an **independent** layout instance |
| **Page edits** | Editing a page **never** modifies the original template |
| **Template updates** | Publishing a new template version **never** silently changes existing pages |
| **New pages** | Always use the **latest published** template version |
| **Future compare/update** | Optional manual “compare / re-apply skeleton” tooling later—**no automatic overwrite** (PR #16 §1.6) |

Templates remain **insert/copy starters** (wave 1)—not route-bound page types. Routes stay ordinary CMS pages. Shared sync continues via **Reusable Blocks**.

### 1.1 Page lifecycle actions

| Action | Behavior |
|--------|----------|
| **Draft** | Page unpublished; incomplete required fields may block publish per template contract |
| **Publish** | Page available on its slug after validation (required sections / SEO / Roles Matrix where applicable) |
| **Archive** | Page removed from public serving; retained for history/restore (product detail later) |
| **Clone** | Create from **template** again (fresh placeholders)—same as choose-template |
| **Duplicate** | Copy an **existing page** (layout + content) to a new draft—still independent |

## 2. Template metadata (every catalog entry)

| Field | Meaning |
|-------|---------|
| **Template ID** | Stable slug id (e.g. `tpl-service-detail`) |
| **Display Name** | Human label in “Choose Template” |
| **Category** | Marketing · Content · Legal · Utility · Campaign |
| **Version** | Opaque revision (e.g. `1.0.0`); bumps on catalog publish |
| **Status** | `draft` · `published` · `deprecated` |
| **Tags** | Search/filter labels |
| **Description** | Short purpose blurb |
| **Supported page types** | Logical type tag(s) (not route binding in wave 1) |
| **Default thumbnail** | SVG preview at `/templates/previews/{templateKey}-thumb.svg` (cover: `-cover.svg`) — generated by `scripts/generate-template-preview-svgs.mjs` |

Catalog tables below include these fields. Thumbnails ship as admin-served SVGs (PR #59).

**Implementation status (PR #59):** 28 platform starters are seeded with full Craft layouts via `db:seed`. Metadata in `packages/template-registry/src/catalog.ts` mirrors `BUILTIN_SKELETON_SEED_DEFS`. Deferred: Coming Soon, Maintenance, Login, Signup.

## 3. Shared quality defaults (all templates)

Unless a template overrides:

| Concern | Default expectation |
|---------|---------------------|
| **SEO** | Unique title + meta description; H1 once; descriptive slug; Open Graph optional later |
| **Accessibility** | Semantic headings; alt text on meaningful images; sufficient contrast; keyboard-reachable CTAs/forms; don’t rely on color alone |
| **Responsive** | Follow existing breakpoint model; stacks on mobile; hero/media scale; cards → 1 column; hide empty **optional** sections only (PR #18 §2.6) |
| **Empty content** | No lorem on publish; required empties stay visible and/or fail validation |
| **Chrome** | Prefer Reusable Blocks for Nav/Footer; reduced chrome = Nav/Footer only (Hero + SEO still required) |

## 5. Website starter kits

A **starter kit** bundles templates + suggested chrome + theme direction for a site type. Kits are **catalog groupings**—not a new runtime engine.

**Platform object model** (kit ID, apply behavior, customization): [cms-operations.md §5](./cms-operations.md).  
**Creating a website from a kit** (later) copies included templates’ latest published versions and suggests default Reusable Blocks—never silently overwrites existing pages.

## 6. Future extensibility

New templates and packs are **catalog entries** composed from existing section/component families.

| Addition | How |
|----------|-----|
| **Portfolio templates** | Generic Content + Gallery/Cards; or new catalog template using Gallery family |
| **Event / Webinar templates** | Landing + Forms + Timeline; optional future Event section family |
| **Product launch templates** | Landing kit variant + Thank You |
| **Campaign landing pages** | Duplicate `tpl-landing`; Experiment optional |
| **Ecommerce landing pages** | Landing + Cards/Pricing; no platform redesign |
| **Industry packs** | Starter kits that preselect Industry/Service Detail + shared Reusable Blocks |

**Rules:** do not fork `HomepageHero`-style components; do not silently rewrite existing pages; bump template version on breaking skeleton changes; kits only reference published template IDs.

## 8. How platform operations & runtime build on this

**Completed (documentation):** [cms-operations.md](./cms-operations.md) defines template registry, lifecycle, versioning, create-website/page flows, kit platform rules, themes/i18n, runtime roadmap, and AI as a deferred future enhancement.

Runtime implementation should:

1. Persist catalog entries (IDs, version, status, metadata) matching §2 and [cms-operations §1](./cms-operations.md).  
2. Publish/archive without mutating existing pages (§1; [cms-operations §2–§3](./cms-operations.md)).  
3. Resolve “latest published” for Create Page.  
4. Optionally store kit definitions (§5) as groupings of template IDs ([cms-operations §5](./cms-operations.md)).  
5. Provide thumbnails as media refs.  
6. Follow runtime phases in [cms-operations §10](./cms-operations.md) (Registry → Create Website & Create Page → Reusable Blocks → Theme → Localization → Cloudflare). AI is **not** a roadmap phase ([§9](./cms-operations.md)).  
7. **Not** implement drag/drop beyond choosing a template id unless scoped separately.
